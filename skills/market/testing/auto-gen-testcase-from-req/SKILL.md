# 功能测试用例自主编写

## 边界

本项目输出功能测试用例设计稿，不包含自动执行器；执行由人或外部测试平台完成。`📷` 是截图节点标记，不代表机器人会自动截图。

本技能规定质量、证据和输出约束，不规定固定流程。是否提问、取证、拆分、保存、修改或导出，由你根据用户意图、信息完整度、风险和当前工作区自主决定。MCP、DWS、Web、项目手册和 UI 证据都是可选来源，不是必经步骤；没有必要时不要为了走流程而调用工具。

## 硬约束

- 不编造页面行为、业务规则、权限、提示、异常处理、真实账号、记录、ID、金额或数量。
- 用户最新明确要求优先。截图或实测与文档冲突时，以可见行为编写，并记录差异或待确认项。
- 需求不完整时，只提出会阻塞可靠设计的问题；不阻塞的部分继续完成并标注假设。
- 每条用例只验证一个清晰目的，前置条件、操作步骤和预期结果必须可观察、可执行。
- 测试方法只使用：需求分析法、等价类划分法、边界值分析法、场景法、错误猜测法，或其 `+` 组合（如 `需求分析法+场景法`、`等价类划分法+边界值分析法`）。
- 最终交付固定为七列，不增加数据列；依赖数据写入实际使用它的步骤。
- 最终编号、排序、去重、统计、数据清单和追溯由 `testcase_compile` 生成，不手工维护最终编号。

## 工作区协作

一次性、信息完整的小请求可以直接回答或生成文件（可用 `artifact_generate`），不必创建工作区。需要跨消息、跨批次持续修订，或用户明确要求保存草稿时，使用测试用例工作区。

若开启了按需工具套件且当前工具列表中未见 `testcase_workspace_*`，先调用 `activate_tools(suite="testcase_workspace")` 激活套件。

- `testcase_workspace_list`：需要恢复或切换已有工作时列出当前或跨会话工作区。
- `testcase_workspace_get`：默认读摘要；只有需要细节时再读取 requirements、cases、evidence、risks、defects、versions 等部分（支持按模块、状态筛选）。
- `testcase_workspace_select`：用户明确继续旧工作区或当前绑定不是目标时，先从列表选择，再读取或修改。
- `testcase_workspace_create`：创建新的独立编写空间。
- `testcase_workspace_update`：增量提交本次变化，同一轮尽量合并为一次调用并传入最近一次读取的 `baseRevision`；冲突时按返回的最新 revision 合并重试，不静默覆盖。工作区完结后可设 `archived: true` 归档，避免干扰后续新需求。
- `testcase_compile`：生成确定性完成版本，可用 `selection` 只合稿回归子集；`deliver=true` 时才发送文件（控制台会话则在工作区生成文件并提示去「测试用例库」下载）。

草稿使用稳定语义 ID，例如 `draft-order-create-valid`。后续补充、修改或作废仍引用该 ID，不依赖会变化的最终编号。需求、证据、决策和待确认问题也使用稳定 ID。传入 `preconditions`、`steps`、`expectedResults` 数组时直接写纯文本原子动作，不要自带 `1.` 序号前缀（编译器会自动编号并避免双重序号）。

## 决策指引

- 用户已经给出足够信息时，直接设计；信息不足但风险低时，可先写草稿并标注假设。
- 需要确认线上行为、企业数据或文档内容时，再选择当前可用且有权限的工具。工具失败时记录证据缺口，不重复盲试，也不把失败当成业务事实。
- 只在“结果会因答案不同而显著变化”时提问；可合并成一组简短问题，避免逐个打断用户。
- 按风险和价值决定覆盖深度，不为凑数硬造说明性章节或用例。
- 新证据与原假设冲突时，更新对应需求、证据和草稿；过时内容标记 `superseded`，不要删除审计线索。
- 相同草稿应复用稳定 ID 更新；完全重复由编译合并，近似重复由编译标记，不擅自合并语义不同的用例。

## 公司业务取证（点宝 / 企业 AI 中台）

`mcp__enterprise__chat` 是公司业务问答入口（点宝），可回答业务规则、内部黑话、字段口径与真实流程。它是可选证据来源，不是必经步骤：只有当思维链确实缺公司业务事实、且需求文档与已有证据没有覆盖时才调用。

值得取证的信号：

- 计费、分成、结算、退款、优惠叠加等金额口径与生效顺序。
- 风控、审核、准入、限额、时效与有效期规则的具体阈值。
- 角色与权限矩阵、审批链路、状态机的合法流转与非法跃迁。
- 字段与枚举的业务含义、跨系统同一对象的口径差异。
- 内部黑话、项目代号、业务缩写对应的真实对象。

不必取证：文档已写明的规则、纯 UI 交互与文案、通用测试方法、可用 `{{DATA: …}}` 表达的未知数据。

调用与落证据：

- 一次问清一个业务事实，问题带模块与场景上下文；同一事实不反复追问。
- 返回是业务口径，不是页面实测行为；与文档或截图冲突时按硬约束处理，并在证据里写 `conflictsWith`。
- 用 `testcase_workspace_update` 落 `evidence`：`type` 为 `mcp`，`sourceRef` 写 `mcp__enterprise__chat：<问题摘要>`，`scope` 写业务域或模块，`summary` 写可验证结论，`confidence` 按明确度取 high / medium / low，并关联 `requirementIds`；用例通过 `evidenceIds` 引用。
- 节点未启用、超时或答非所问时，记录证据缺口与待确认问题，退回文档加假设标注；不重复盲试，不把失败当业务事实，不编造规则。

## 用例设计约束

### 覆盖

提取功能、角色、权限、输入输出、状态变化、依赖、异常和边界。有输入约束时覆盖有效类、无效类和边界值；有流程时覆盖正常、异常中断和分支。核心功能标高优先级，次要功能标中，辅助展示标低。

### 拆分

- 每条用例一个验证目的；同一能力跨 Tab 或列表复用时写通用用例，字段、筛选、菜单、权限或规则不同才拆分。
- 列表页通常关注范围、字段、筛选、搜索、排序、分页、批量操作、行内操作、状态和日志，但按实际需求取舍。
- 业务规则、限制、时效、有效期和状态规则应形成独立可验证用例。
- 时间窗口覆盖有效期内和超过有效期；需求给出边界时覆盖第 X 天和第 X+1 天。
- 外部系统产生的数据不得跳过，使用真实数据占位符，并通过当前系统可见字段、标识、入口、提示或日志验证。

### 业务纵深

标准功能用例之外，按取证到的真实业务再补一层公司场景，让用例贴近实际运营而不是通用模板：

- 用真实角色与权限组合替代泛化的“管理员 / 普通用户”，覆盖越权、跨组织与数据可见范围。
- 串联真实业务流（如提交 → 审核 → 生效 → 结算 → 对账 → 售后），覆盖中断、回退、重复提交与并发。
- 把业务口径写成可断言的数值与状态：金额精度与舍入、分成比例、限额阈值、时效窗口、状态非法跃迁。
- 标题与预期使用公司真实字段名、枚举值与黑话；未知实体仍用占位符，不编造 ID、金额与记录。
- 取证未覆盖的业务点标注假设或待确认，不用想象补齐。

## 评审风险、缺陷与回归

同一个工作区还承载需求评审、缺陷复现、执行回填与回归推荐。用户提出这些诉求时复用当前工作区，不新建，也不把这些内容塞进七列正文。

- 需求评审：口径缺失、规则冲突、边界未定义写成 `risks`（`severity` 高 / 中 / 低，`status` open / mitigated / accepted，`mitigation` 写缓解动作）。未关闭风险应有用例覆盖，覆盖不了要说明原因；用户明确接受后改 `accepted`。
- 缺陷复现：已知缺陷写 `defects`（`sourceRef` 填缺陷单号，`status` open / fixed / verified / rejected），复现或回归用例用 `defectIds` 关联。已修复缺陷缺复现用例时合稿会告警。
- 执行回填：用户回报结果时在对应草稿写 `execution`（`status` untested / passed / failed / blocked，可带 `executor`、`note`）。失败与阻塞写清现象，不替用户判定通过。
- 回归范围：合稿按上轮失败与阻塞、未关闭风险、待验证缺陷、高优先级给出建议范围。用户只要回归子集时给 `testcase_compile` 传 `selection`（`modules` / `requirementIds` / `caseIds` / `priorities` / `executionStatuses`，多条件同时生效），不手工删用例。
- 测试报告：有执行记录时合稿输出通过率、失败与阻塞说明。如实呈现未执行数量，不用总数掩盖未执行。

## 七列输出契约

`用例编号 | 用例标题 | 前置条件 | 操作步骤 | 预期结果 | 优先级 | 测试方法`

- 用例编号形如 `TC_MODULE_001`，同模块连续，正常场景在前，异常和边界在后。
- 标题描述角色、数据特征或规则条件及验证目的。
- 前置条件包含账号、权限、依赖数据和必要环境状态，只描述角色与已登录状态，不附登录实现方式。
- 步骤写明业务页面路径、UI 元素、动作及直接输入值或占位符；不把预期写入步骤。
- 预期结果描述具体元素、文案、数值或状态变化，禁止“功能正常”“返回成功”“系统正确处理”等模糊表述。
- 优先级为高 / 中 / 低；测试方法使用上述五种名称或其 `+` 组合（最多 3 种，主方法在前）。

前置条件、步骤和预期结果从 `1.` 开始，多项用 `<br>` 分隔。每步一个原子 UI 动作；顶部菜单、行内菜单和批量操作按“选择记录 → 点击入口 → 展开或选择菜单项 → 确认”展开。默认在关键断言、失败现场和必要状态处添加 `📷`；用户要求移除时全部删除。

## 数据参数

测试人员主动输入、选择或上传的内容可给出合理代表值。边界和等价类场景必须覆盖下限、上限及相邻无效值。

系统中已存在且无法预知的账号、记录、ID、金额或数量必须使用 `{{DATA: 数据描述}}`。占位符简短、单一、可查找；对比条件使用独立占位符；预期数值引用真实基准或相对变化。

把筛选值写入筛选步骤、搜索词写入搜索步骤、目标记录写入定位步骤、输入值写入输入步骤、导出字段写入表头核对步骤。不新增“准备数据”“使用以下数据”等独立操作步骤。

## 完成版本

编译结果包含：标题与来源、概要统计、需求缺失或假设、按模块组织的七列用例、模块级数据准备清单、需求追溯、待确认问题和编译告警；有相应数据时还包含需求评审风险、缺陷复现追溯、执行结果与测试报告、回归范围建议。近似重复、缺失需求或证据、空内容等问题应如实保留，不为了“完成”而隐藏。

每个模块说明对应需求章节和自动化可行性：可自动化 / 部分可自动化 / 暂不可自动化，并给出客观原因。存在人机校验、外部通知或人工审批时通常为部分可自动化；依赖真实支付、硬件、生产专属数据或不可逆操作时通常为暂不可自动化。

## 交付前自检

- 七列表头固定，所有用例列数一致。
- 每条用例只有一个验证目的，步骤原子，预期具体可观察。
- 输入值和依赖数据写在实际步骤中，没有独立数据步骤。
- 依赖数据使用简短单一占位符，没有编造实体或数值。
- 数据清单与最终用例编号一致，需求追溯完整。
- 截图标记符合用户要求，统计与编号一致。
- 正常、异常、边界、权限、时间窗口和外部系统规则已覆盖，或说明未覆盖原因。
- 测试方法与步骤、断言匹配，工作区 revision 无冲突。
- 业务规则类用例挂接了证据或标注了假设，业务口径没有被当成页面实测行为。
- 未关闭风险与待验证缺陷有覆盖或说明，执行结果按用户实际回报回填，回归子集通过 `selection` 而非删改用例得到。
