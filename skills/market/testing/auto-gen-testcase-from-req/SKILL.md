# 系统需求文档生成功能测试用例

## 本项目适配说明

本项目没有自动执行器：输出是功能测试用例文档，执行由人或外部测试平台完成，不要承诺"可直接执行"。
`📷` 只是截图节点标记，本项目不会真的截图；文档产出用 `deliver_artifact` 交付，正文文本直接回复。

## 目标

生成可追溯、字段完整且不编造业务行为的功能测试用例文档（不含自动执行器，执行由人或外部测试平台完成）。

## 输入

- 必选：系统需求文档或可验证的功能说明。
- 可选：模块范围、重点场景、输出路径、系统 URL、页面路径、账号角色、截图、录屏、实测结果和用户修正意见。

## 必读参考

- 生成或修改用例前，读取 `references/testcase-splitting-rules.md`，按其拆分字段、筛选、汇总、公式、菜单、规则和空值场景。
- 选择测试方法前，读取 `references/test-methods.md`，只使用其中的方法名称。
- 生成文件、适配测试管理平台或需要完整格式时，读取 `references/output-example.md`。

## 1. 证据与用户要求

证据优先级：

1. 用户最新修正意见、最新截图和最新实测结果。
2. 真实 UI、截图和录屏。
3. 需求文档中的明确要求。
4. 官方文档、SOP 和参考资料。

执行要求：

- 写用例前列出页面控件：Tab、筛选、搜索、按钮、菜单、表格列、排序、分页、弹窗和状态标识；每项映射到用例或说明不覆盖原因。
- 截图或实测与 PRD 不一致时，以可见 UI 编写操作，并在“需求缺失或假设”中记录差异。
- 新证据确认原待确认能力时，同步更新用例、统计、数据准备清单、关注点和自动化可行性，清除过期表述。
- 用户对章节、数据写法和截图标记的明确要求优先；只覆盖用户点名的格式，其余规则保持不变。
- 用户要求按业务页面编写时，把公共预警展示、筛选联动和下钻写入各对应页面，不单建通用章节。
- 用户要求移除截图图标时，删除全部 `📷`，并停用截图节点自检。
- 测试用例文档只描述账号角色、权限和已登录状态，不附加登录实现方式。

## 2. 解析与覆盖

- 提取功能、流程、角色、权限、输入输出、状态变化、依赖、异常、边界和对应需求章节。
- 每个功能点明确前置条件、UI 路径、触发动作和可观察结果。
- 核心功能标高优先级，次要功能标中，辅助展示标低。
- 需求有输入约束时覆盖有效类、无效类和边界值；有流程时覆盖正常、异常中断和分支。
- 说明性章节不硬造用例，应说明其映射到哪些可执行用例或数据准备项。

## 3. 用例拆分

- 每条用例只验证一个清晰目的；详细粒度遵循 `references/testcase-splitting-rules.md`。
- 同一能力在多个 Tab 或列表复用时写成通用用例；字段、筛选、菜单、权限或规则不同才拆分。
- 列表页按“范围 → 字段 → 筛选 → 搜索 → 排序 → 分页 → 批量操作 → 行内操作 → 状态 → 日志”组织。
- 业务规则、限制、时效、有效期和状态规则默认生成 `TC_RULE_001` 类用例。
- 时间窗口至少覆盖有效期内和超过有效期；需求给出边界时覆盖第 X 天和第 X+1 天。
- 外部系统产生的数据不得跳过，使用真实数据占位符，并通过当前系统可见字段、标识、入口、提示或日志验证。

## 4. 固定列结构

所有用例固定为七列：

`用例编号 | 用例标题 | 前置条件 | 操作步骤 | 预期结果 | 优先级 | 测试方法`

| 字段 | 要求 |
|---|---|
| 用例编号 | 使用 `TC_MODULE_001`；同模块连续，正常场景在前，异常和边界在后 |
| 用例标题 | 描述角色、数据特征或规则条件及验证目的 |
| 前置条件 | 包含账号、权限、依赖数据和必要环境状态 |
| 操作步骤 | 写明页面路径、UI 元素、动作及直接使用的输入值或占位符 |
| 预期结果 | 描述具体元素、文案、数值或状态变化 |
| 优先级 | 高 / 中 / 低 |
| 测试方法 | 只使用 `references/test-methods.md` 中的方法 |

不得增加额外的数据列；所有输入值和依赖数据按第 6 节写入实际使用它们的步骤。

## 5. 编号、步骤与断言

- 前置条件、操作步骤和预期结果都从 `1.` 开始；表格内多项用 `<br>` 分隔，单项也保留 `1.`。
- 前置条件每项只描述一个账号、权限、数据或环境状态；预期结果每项只描述一个主要断言，不用分号串联独立内容。
- 步骤格式：`{序号}. [导航到页面→] 操作元素[，输入/选择参数]。{📷}`。
- 每步只写一个原子 UI 动作，明确页面路径和元素名；不得使用“完成操作”“进行设置”等不可执行描述。
- 操作路径优先使用业务页面或菜单名称；技术 URL 只放在来源或备注中，除非用户要求保留。
- 不把预期写入步骤。顶部菜单、行内菜单和批量操作按“选择记录 → 点击入口 → 展开/选择菜单项 → 确认”展开。
- 预期结果按页面出现、数据刷新、状态变化或后续影响排序，禁止“功能正常”“返回成功”“系统正确处理”等模糊表述。
- 默认在关键断言、失败现场和必要状态处添加 `📷`；已执行的 UI 用例至少保留一个断言截图节点，除非用户要求移除。

## 6. 数据参数

### 6.1 输入值

测试人员在步骤中主动输入、选择或上传的内容可直接给出合理值。边界和等价类场景必须给出代表值，例如长度下限、上限及相邻无效值。

### 6.2 依赖数据

系统中已存在且无法预知的账号、记录、ID、金额或数量，必须使用 `{{DATA: 数据描述}}`，禁止编造。

- 占位符只描述数据本身，保持简短、单一、可查找；不写“具体参数”“多组条件”“根据实际情况”等元说明。
- 对比场景中的条件 A/B、有效/无效、边界内/外必须使用独立占位符。
- 预期数值引用真实基准或相对变化，不编造绝对值。

### 6.3 写入原步骤

- 把筛选值写入筛选步骤、搜索词写入搜索步骤、目标记录写入定位步骤、输入值写入输入步骤、导出字段写入表头核对步骤。
- 不新增“准备数据”“使用以下数据”或“根据数据定位记录”等独立操作步骤。
- 正确示例：`在“店铺”筛选框选择 {{DATA: 存在成本异常记录的店铺}}，点击“查询”。`
- 错误示例：`选择 {{DATA: 异常数不同的多组条件}} 中的条件 A。`

### 6.4 模块级数据准备清单

每个模块表格前汇总该模块全部占位符，并标明使用它们的用例编号；拆分、删除或顺延用例后同步更新引用。

```text
> ⚠️ 数据准备清单（执行前必读）
> 1. {{DATA: 具有目标页面权限的账号}} — 用于 TC_MODULE_001 至 TC_MODULE_003
> 2. {{DATA: 满足目标规则的真实记录}} — 用于 TC_MODULE_001
```

## 7. 不明确需求

- 不假设需求未说明的页面行为、数据规则、权限、提示或异常处理。
- 缺失信息阻塞可靠生成时提出简短问题；不阻塞时继续生成，并在“需求缺失或假设”中记录。
- 规则完全不可观察且无法准备数据时，可不生成用例，但必须说明原因和所需补充信息。

## 8. 自动化可行性与追溯

每个模块末尾写：

- `对应需求文档章节：...`
- `自动化可行性：可自动化 / 部分可自动化 / 暂不可自动化。原因...`

判定：步骤、断言和数据明确且无外部依赖为可自动化；存在人机校验、外部通知或人工审批为部分可自动化；依赖真实支付、硬件、生产专属数据或不可逆操作为暂不可自动化。只描述客观阻塞，不在用例文档中添加登录实现说明。

## 9. 输出组织

输出标题、来源、概要统计、需求缺失或假设、按需求章节组织的用例、数据准备清单、章节追溯和自动化可行性。

- 章节默认与需求文档大小章节对齐。
- 跨章节能力放在主功能章节，说明性章节写映射关系。
- 按业务页面编写时，公共能力分别落入对应页面。
- 生成文件或适配平台时使用 `references/output-example.md` 的骨架。

## 10. 生成后自检

- [ ] 七列表头固定，所有用例列数一致且无额外数据列。
- [ ] 前置条件、步骤和预期结果从 `1.` 开始，多项使用 `<br>`。
- [ ] 输入值和依赖数据均写入实际使用它们的原步骤，没有独立数据步骤。
- [ ] 依赖数据均使用简短、单一的占位符，无编造实体、ID、金额或数量。
- [ ] 每个模块的数据准备清单完整，编号引用与表格一致。
- [ ] 前置条件包含账号、权限和必要数据，未附加登录实现方式。
- [ ] 预期结果具体可观察，对比数值使用真实基准或相对引用。
- [ ] 截图规则符合用户要求：默认有断言节点；要求移除时不存在图标。
- [ ] 用例数量、优先级统计、模块数和编号重新统计后一致。
- [ ] 章节与需求对齐，公共能力已按用户要求写入对应页面。
- [ ] 控件清单、Tab 共用/独有能力、菜单和列表功能均覆盖或说明原因。
- [ ] 业务规则、时间窗口、外部系统规则和边界场景已覆盖或说明不可覆盖原因。
- [ ] 字段、筛选、汇总、公式和空值场景符合拆分规则。
- [ ] 测试方法来自 `references/test-methods.md` 且与步骤和断言匹配。
- [ ] 每个模块都有需求章节追溯和自动化可行性说明。

## 异常处理

- 文档无法解析：请求可读取的需求内容或 Markdown 文件。
- 无有效功能点：说明缺少可验证需求。
- 需求不完整：列出缺失内容，必要时请求补充。
- 无法选择测试方法：请求补充功能逻辑或输入输出约束。
