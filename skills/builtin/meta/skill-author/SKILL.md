# 技能编写与优化

## 适用场景

用户要沉淀一类任务的 SOP、把提示词变成技能、改造现有技能，或问“为什么技能没被触发/加载”。

## 步骤

1. 先确认：要解决的任务、典型用户说法、输入与输出、涉及的工具、是否包含写操作。缺关键信息时先问一个最关键的问题。
2. 用 `skill_search` 查重；已有技能能覆盖时优先改造，不新增重复技能。需要参考格式时用 `skill_read` 读取本技能的 `references/skill-template.md`。
3. 设计 frontmatter：
   - `name`：小写字母开头，只含小写字母、数字和连字符，2–64 字符。
   - `description`：不超过 160 字符，写“做什么 + 产出”，不要写口号。
   - `when_to_use`：不超过 200 字符，列 2–4 个真实触发场景和用户会说的词。
   - `version`：语义化版本，如 `1.0.0`。
   - `tags`：包含中文与英文关键词，便于本地路由。
   - `allowed_tools`：只写真实存在的工具名；只读任务不要授予写工具。
   - `risk`：`read` / `write` / `destructive`，按最危险的动作定级。
   - `visibility`：`public` 或 `admin`。
   - `max_instruction_chars`：默认 4000；正文超过上限会被截成大纲，必须拆分或改用参考文件。
4. 正文按「适用场景 / 步骤 / 约束」组织：
   - 步骤用动词开头，写成可执行、可验证的动作。
   - 每个关键步骤写清工具名、动作、必填参数和失败时的退路。
   - 写清哪些内容必须来自工具证据，哪些可以基于用户输入。
   - 写清写操作的风险分级：普通写操作在本人授权后直接执行，取消、覆盖等高危操作才提示 `/confirm`；同时写清脱敏和不可信内容边界。
5. 使用渐进披露：长模板、字段表、检查清单放到 `references/`，正文只保留索引和关键判断；单次 `skill_read` 最多 500 行/4000 字符。
6. 设计测试集：至少 3 条典型用户说法、2 条边界说法（不该触发/信息不足）、1 条含写操作的说法；确认路由能命中，正文能加载，工具名全部存在。
7. 交付方式：
   - 内置技能：提交到 `skills/builtin/<name>/SKILL.md`，重启或等待目录热重载。
   - 本地技能：控制台「技能 Skills」新建，或 `POST /api/v1/admin/skills`；保存后热更新。
   - 校验：控制台校验草稿或 `POST /skills/validate`；重扫用 `POST /skills/reload`。
8. 输出时给出完整 SKILL.md、参考文件清单、测试说法和部署步骤；不要只给一段提示词。

## 约束

- 不发明工具名、参数或返回字段；不确定时先查现有技能或让用户确认。
- 不把密钥、内部地址、客户名单写进技能；示例数据要脱敏。
- 不复制第三方技能正文；参考思路时自己重写，并遵守对方许可证。
- 技能不能绕过审批、确认和权限；写操作必须在正文里明确要求确认。
- 技能只提供流程知识，不引入可执行代码；需要新工具时走插件或 MCP。
