# 对比 DeepSeek Super-agent 与《从 OpenClaw 到 Super Agent》：本项目的差距与改进优先级

> 参考材料
> - A：《从 OpenClaw，怎么走到了 Super Agent？》— spike（腾讯游戏数据团队负责人），产品/组织视角的演进复盘
> - B：《刚刚，DeepSeek 重磅发布全新 Agent 架构：AI 开始指挥 AI 干活》— 爱范儿对 DeepSeek Harness 团队技术文章《Super-agent 设计探索：迈向更自主的 Agent 系统》的转述，原始原型 https://github.com/deepseek-ai/dsh-superagent-prototype
>
> **材料可信度提示**：B 是二手转述，其中的性能数字（p50 12.4min / p95 15.7min、cache token +37%）来自爱范儿的复述，且 DeepSeek 自己声明实验用的是**合成消息 + 模拟耗时工具，并未评估真实编码质量**。落地前建议先读原始技术文章与原型代码，不要把这些数字当既成结论。

## 一、结论先行

本项目（钉钉智能体）在**单体 Agent 的工程完成度**上已经追平甚至超过 DeepSeek 的原型；真正的差距集中在**多任务调度架构**这一层。

**本项目已经领先的部分**（B 文把它们列为「尚未解决的挑战」，本项目已经做完了）：

| B 文列为挑战 | 本项目现状 | 证据 |
| --- | --- | --- |
| 两级过滤（规则 + 大模型） | 做成**三级漏斗**，多出「防抢答 debounce」和「群活跃度抑制」 | [src/bystander/BystanderTriageEngine.ts:326](../src/bystander/BystanderTriageEngine.ts#L326) |
| 安全与隐私：提示词注入、凭据泄露 | 写操作 `/confirm` 闸门 + **执行层**工具白名单（模型被诱导也看不到写工具），`research` Worker 恒只读且无法配置放开 | [src/workers/ScopedToolProvider.ts](../src/workers/ScopedToolProvider.ts) |
| 长期记忆（数周数月难恢复） | 三层记忆 + pgvector + 情景压缩 + 语义记忆的作用域/敏感级/过期时间/跨群授权档位 | README「三层记忆」 |
| 进度可见性与人工批准需重新设计 | AI 卡片流式 + `/job-status` + `agent_job_events` + 控制台 + 用量归因 | README「后台任务队列」 |
| 异常恢复 | 看门狗分级干预（注入约束 → 降级停用工具 → 硬阈值暂停），PG 租约 + `FOR UPDATE SKIP LOCKED`，崩溃后其他实例重新领取 | [src/watchdog/RunWatchdog.ts:260](../src/watchdog/RunWatchdog.ts#L260)、[src/types/jobs.ts:78](../src/types/jobs.ts#L78) |

B 文团队自己在结尾承认：「并没有提出全新的理论，而是将任务调度、缓存管理、事件驱动、存算分离等经典计算机系统思想应用到了 Agent 架构中」。这句话对本项目同样成立 —— 下面列的差距都是**工程编排问题，不是模型能力问题**。

**真正的四个差距**（按严重度）：

1. **没有 Router**：Worker 已存在，但只能由人打 `/worker` 指令触发，模型自己无法分派。
2. **ReAct 同步串行**：同一会话严格排队，长任务会把后续消息全部堵死。
3. **没有事件直通订阅**：`agent_task_subscriptions` 只用于「通知人」，不会把后续事件路由回正在执行的那个任务体。
4. **事件源单一**：只有钉钉消息 + 定时器；GitHub 是只读工具，不是触发源。

## 二、逐项对比：B 文（DeepSeek Super-agent 架构）

| # | Super-agent 能力 | DeepSeek 做法 | 本项目现状 | 判定 |
| --- | --- | --- | --- | --- |
| 1 | 双层架构 Router + Worker | Router 常驻，统一接收群聊/GitHub/邮件，判断分派并维护跨任务上下文；Worker 独立上下文与工具，可再调 Subagent；Worker 完成后向 Router 汇报，由 Router 统一对用户说话 | Worker 三类画像齐备（`research` / `ops` / `report`，[src/workers/WorkerRegistry.ts:36](../src/workers/WorkerRegistry.ts#L36)），Subagent 也有（`delegate_research`，[src/react/SubagentToolProvider.ts:32](../src/react/SubagentToolProvider.ts#L32)）。**但没有 Router**：Worker 唯一入口是人打指令 [src/commands/CommandRouter.ts:294](../src/commands/CommandRouter.ts#L294)，模型看不到任何分派工具 | **缺关键一层** |
| 2 | 订阅 / 事件直通 | Worker 接手 PR 后，后续评论与状态变化**直接发给它**，不再经 Router 重新分派。取消直通后 Router 决策量 +30%，总 cache 读取 2323 万 → 3177 万 token（+37%） | `agent_tasks` + `agent_task_links` 已有 `kind + ref` 幂等绑定（`message` / `conversation` / `job` / `url` / `doc` / `issue` / `card`，[src/db/taskSchema.ts:124](../src/db/taskSchema.ts#L124)），但订阅语义是**通知人**（[src/tasks/TaskService.ts:187](../src/tasks/TaskService.ts#L187)），不回流到执行体 | **完全缺失** |
| 3 | 异步 ReAct Loop | 耗时工具调用转后台，前台会话继续收新消息，完成后再回灌结果；用户可中途改方向或终止。已在 DSH 实现但**未默认开启** | **严格同步串行**：「同一会话严格按到达顺序串行执行，新消息只排队、不会打断进行中的回答」（[src/harness/RunControlRegistry.ts:30](../src/harness/RunControlRegistry.ts#L30)）。唯一逃生口是 `/stop` | **最大差距** |
| 4 | Trigger 多事件源 | 群聊消息、邮件、日程提醒、GitHub 评论、CI 测试结果 | 只有两路：钉钉 Stream 的 @ 消息、DWS 长连接的非 @ 群消息；加上 `src/scheduler` 定时器。**GitHub 是只读工具而非事件源**（[src/github/GithubClient.ts](../src/github/GithubClient.ts)，无 webhook、无轮询）；无邮件、无 CI | **事件源单一** |
| 5 | 两级过滤 | 程序规则快速排除无关消息 → 大模型结合上下文判断是否行动 | 三级漏斗：L1 零 Token 规则（表情/寒暄/冷却/活跃度/主题词预筛）→ 防抢答 debounce 窗口 → L2 低温度、无工具、无思维链的结构化判定 + 置信度门禁 | **本项目更强** |
| 6 | 投机执行 | 「静默复现并修复」：后台复现问题、分析原因、找修复方案；**只有确认问题存在且找到相对简单的修复方法才提交**，否则全程安静 | **同构实现已存在**：`SilentInvestigationService` 对「判定为可疑但不该插话」的消息做后台只读查证，执行层只暴露 `risk=read` 工具，确定性证据评分（模型自评 35% + findings/sources），达标才浮出，否则「连『我查过』都不说」，全程写 `silent_investigations` 审计表（[src/bystander/SilentInvestigationService.ts:233](../src/bystander/SilentInvestigationService.ts#L233)） | **骨架已有，深度不足**（只读检索，不复现、不产出修复） |
| 7 | 存算分离 | 执行循环在云端，会话状态入库，**代码仓库/文件/工具链留在用户设备**；本地只部署轻量 daemon 接收云端命令；设备离线后重新上线继续执行 | 方向相反：执行循环与状态都在服务端 PG，仓库靠 `PROJECT_ALLOWED_ROOTS` 索引到服务端。但「进程崩溃续跑」已通过租约 + `SKIP LOCKED` 解决 | **不适用**（部署形态不同，见第五节） |
| 8 | Watchdog | 独立 AI 监督员，检查任务是否有进展、是否陷入无效循环，发现异常时**尝试修复** | 规则式看门狗：检测连续无新信息、相同工具+参数重复调用、连续多步工具失败、Token/墙钟预算告警比例；分级干预到 `degrade`（停用工具强制作答）与 `pause`/`cancel`（[src/watchdog/RunWatchdog.ts:298](../src/watchdog/RunWatchdog.ts#L298)），写 `watchdog` 流事件与指标 | **本项目更可控**，但不「尝试修复」，只暂停等人 |
| 9 | 分派层用轻量模型 | Router 只做信息理解与任务分派，轻量模型即可胜任；强模型用于复杂执行 | 有按群模型路由（`group_model_routes`）、旁听判定刻意用低温无工具无思维链。但因为没有分派层，拿不到「分派层降级省钱」这份收益 | **随 #1 顺带获得** |

## 三、逐项对比：A 文（产品与组织演进）

A 文不是架构文，讲的是 Agent 产品的演进逻辑。对本项目更有价值的是它的几个判断：

| # | A 文观点 | 本项目现状 | 判定 |
| --- | --- | --- | --- |
| 1 | Bot 与 Working Agent 双向收敛：Bot 补工作台/文件/连接器，Working Agent 补手机与群入口 | 纯 Bot 形态（钉钉）。有管理控制台、项目手册、工作区文件读取，但**没有「人和 Agent 围绕同一件事协作」的工作面**（左侧资料、中间可改内容、旁边会话、下面跑工具） | 部分缺失，但对本项目定位未必是问题 |
| 2 | 「我希望的是同一件事能继续，而不是每换一个地方就认识一个新助手」— 跨入口接续同一执行会话 | `conversationKeyFor` 把单聊与群聊切成不同会话键（[src/harness/AgentHarness.ts:182](../src/harness/AgentHarness.ts#L182)）。`agent_tasks` 可以 link 多个 conversation/message/job，算**弱接续**；但「手机上补一句 → 接回正在跑的那个执行」没有 | **有基础，未打通** |
| 3 | 从自己用到和别人一起用：用户在自己 Agent 里提问 → 需求进入有专业同学 + 数据 Agent 的工作群 → 补充口径 → 结果回到用户原来的工作 | 有群工作区、群目标/群任务、分层人设、技能与插件分发。但**没有跨 Agent 的需求交付链路**（一个 Agent 把需求交给另一个 Agent + 专业人，结果回流） | 缺失，依赖多机器人（当前不在范围内） |
| 4 | 工作环境本身也可以让 Agent 参与建设：Context + Harness；Mods 机制让用户改提示/工具行为/界面并可让 Agent 自己写 Mod；DSH Creator mode 支持**对话创建插件** | 有 `skill-author`、`plugin-author` 两个内置技能（**只是说明书**）。Agent 侧的技能工具全是只读：`skill_search` / `use_skill` / `skill_read`（[src/tools/skills/SkillToolProvider.ts:50](../src/tools/skills/SkillToolProvider.ts#L50)），没有任何 `risk=write` 的落盘工具。技能与插件只能管理员在控制台手写 | **明确缺失** |
| 5 | 用顺的 Agent 帮忙带一个新 Agent（Coach）：让成熟 Agent 去看目标 Agent 的会话，回到来源核对，再帮它调整 | 代码库中无 coach 相关实现（全仓检索无命中） | **完全缺失**，但当前不该做（见第五节） |
| 6 | 不满意时不要只加「你要认真一点」式规则；先让它看实际过程：用了哪些材料、哪一步出问题、我们对「做好」的理解差在哪，再决定补背景/改说明/调工具 | 有 `src/eval`（golden set + flow eval）、审计表、用量流水、思维链与工具轨迹落库。**材料齐备但没有闭环**：没有让 Agent 读自己的运行轨迹并提出 harness 修改建议的机制 | 半成品 |
| 7 | 插件与程序仍要在机器上执行：来源、权限、可恢复版本都要看；涉及账号、外发、付费**不能因为「AI 帮我装的」就省掉确认** | 已经完全符合：插件是纯声明包不执行安装脚本，安装校验任何 error 都不落盘，保留最近两个版本可回滚，写操作走 `/confirm` | **已达标** |

A 文里最值得直接抄的，是它记录的 Coach 实验中三个**具体失败模式**（第 79–80 行）：

- 把「已经记下来了」理解成「相关的人已经接手」；
- 没注意到后面取消了安排，继续拿旧信息提醒；
- 纠正之后又变得太谨慎，只敢列事实，把判断全交回来 —— 而作者要的恰恰是**有依据的判断**，不是一张需要自己处理的清单。

这三条与本项目的「主动播报 / 个人提醒 / 群目标进度」功能高度相关，应该直接转成 eval 用例（见 P0-4）。

## 四、改进项按性价比排序

评分维度：**收益**（是否解锁新能力 / 解决已知痛点）÷ **成本**（代码量 + 是否触碰已稳定的线上链路 + 验收难度）。

### P0 — 高性价比，建议立刻做

#### P0-1　给模型一个 `dispatch_worker` 工具（Router 的第一步）

- **现状**：Worker 画像、工具白名单、独立预算、结构化回执、持久化队列、租约、用量归因**全部已就绪**。唯一缺的是「模型自己能用」。
- **要做什么**：新增一个 ToolProvider，把 `/worker <research|ops|report> <需求>` 的能力以工具形式暴露给主 Agent，参数为 `worker` + `task`，执行即落 `agent_jobs` 并立刻返回任务 ID。
- **为什么值**：这是 DeepSeek 双层架构里「AI 当主管」的最小可用版，而本项目 **90% 的底座已经在**，改动集中在一个新文件。它同时缓解 P0-2 —— 因为分派出去的任务立即返回，前台不再被长任务占住。
- **成本**：约 1 天。
- **风险与对策**：
  - 递归委派 → 照抄 `SubagentToolProvider.visibleProviders()` 排除自身的做法（[src/react/SubagentToolProvider.ts:106](../src/react/SubagentToolProvider.ts#L106)），且 Worker 内部不挂载 `dispatch_worker`。
  - 权限提升 → 工具过滤必须在**执行层**由 `ScopedToolProvider` 完成，不能只靠提示词；`research` 恒只读的现有约束不能被这个工具绕过。
  - `ops` Worker 的非 DWS 写操作与 DWS 高危操作**仍需 `/confirm`**，分派不等于授权。
- **验收**：群里 @ 机器人提一个需要多轮检索的需求，观察它是否自主分派给 `research` 并立即回执任务 ID；`/job-status` 能看到 `worker=research`；用量流水归因正确。

#### P0-2　异步 ReAct：长耗时工具转后台，前台会话不阻塞

- **现状**：`RunControlRegistry` 明确「同一会话严格按到达顺序串行执行，新消息只排队、不会打断进行中的回答」。用户在群里问一个需要跑 3 分钟的问题，这期间他补的第二句话只能干等。
- **要做什么**：**不重写 ReAct**。在工具层加「转后台」语义 —— 当单个工具调用（或整轮）耗时超过阈值时，把它落成 `agent_jobs`，前台立即回执「已转入后台，任务 ID xxx，完成后单聊通知你」，完成后走**已有**的单聊通知链路。
- **为什么值**：这是 B 文里对用户体感改善最直接的一条，而本项目可以完全复用已有的队列、租约、重试、看门狗、通知、审计 —— 相当于给现成的持久化队列加一个自动触发入口。
- **成本**：约 2 天。
- **风险与对策**：
  - 结果回灌时机 → 先只做「完成后单聊通知发起人」，不做「插回原群会话」，避免打乱群上下文。
  - DeepSeek 自己也是「已实现但**未默认开启**」→ 说明这条应该灰度：加 `ASYNC_REACT_ENABLED` 开关，默认 false，按群逐步放开。
  - 与看门狗的交互 → 转后台后预算主体从「交互运行」变成「job」，硬阈值行为会从 `cancel` 变成 `pause`（[src/watchdog/RunWatchdog.ts:298](../src/watchdog/RunWatchdog.ts#L298)），这个语义变化要在文档里写清。
- **验收**：单聊发一个必然长耗时的需求，3 秒内拿到「已转后台」回执；紧接着发第二句话能立即得到响应，不排队。

#### P0-3　事件直通订阅：把 task subscription 从「通知人」升级为「路由回执行体」

- **现状**：`agent_task_links` 已经能把 `message` / `conversation` / `job` / `url` / `doc` / `issue` / `card` 幂等绑定到线程上，但后续事件不会回流到那个执行体。
- **要做什么**：入站事件（群消息、后续的 GitHub 评论等）先查一次「是否有活跃 task 绑定了这个 ref」；命中则把新事件**追加进该 task 的执行上下文**，而不是开一轮全新会话。
- **为什么值**：这正是 DeepSeek 省下 37% cache token 的机制，也是 A 文反复强调的「同一件事能继续，而不是每换一个地方就认识一个新助手」。本项目的数据模型**已经为此准备好了**，缺的只是查询与注入逻辑。
- **成本**：约 2–3 天。
- **风险与对策**：
  - 误绑定 → 命中条件要保守（同 `kind + ref` 且 task 处于活跃状态且未过期），并在回执里显式说明「已并入任务 xxx」，让人能纠正。
  - 上下文膨胀 → 只追加增量事件，配合已有的情景记忆压缩。
- **验收**：`/task new` 建线程并 link 一个群话题，随后在同一话题里补充条件，确认新条件进入了该任务的执行上下文而非新开一轮。

#### P0-4　把 A 文记录的三个失败模式写进 eval（半天，别和 P2-1 混在一起）

- **要做什么**：在 `src/eval` golden set 里加三个用例：
  1. Agent 记下了一件事 → 断言它**不得**表述为「相关人员已接手」；
  2. 安排被取消后 → 断言它**不得**继续用旧信息提醒；
  3. 被纠正过度之后 → 断言它仍要给出**有依据的判断**，而不是只列事实把决策全推回给人。
- **为什么值**：成本极低（复用现成 eval 框架），而这三条正好命中本项目已上线的「主动播报 / 个人提醒 / 群目标进度」功能。这是别人踩过的坑，白拿。
- **成本**：约半天。

### P1 — 中等性价比，做完 P0 再评估

#### P1-1　GitHub 从「只读工具」升级为「只读事件源」

- **现状**：`GithubClient` 提供 5 个只读工具，无 webhook、无轮询。GitHub 只能被模型主动查，不能主动触发。
- **要做什么（第一步，保守版）**：PR 评论 / issue 新建 / CI 失败 → 通过 webhook 或轮询进入 Trigger 管道 → 复用旁听三级漏斗判定是否值得行动 → 命中则走 `SilentInvestigationService` 做后台只读分析 → 结论回到绑定的钉钉群。**不自动提交 PR、不引入写权限。**
- **为什么值**：B 文的旗舰场景是「群里讨论 Bug，Agent 后台复现并提交 PR」。研发协作是价值最高的事件面，而本项目已经有「群 ↔ 任务线程」的绑定基础（P0-3）。
- **成本**：约 3–5 天（webhook 接收 + 鉴权 + 事件归一 + 接入现有漏斗）。
- **风险与对策**：
  - 引入写权限是**质变而非量变**，涉及外发与代码修改，必须单独决策，不要和只读事件源捆在一起做。
  - 企业内网 GitHub 有主机白名单与网络可达性问题（`GITHUB_ALLOWED_HOSTS`）；本项目历史上已经踩过外部系统权限坑（DWS 跨组织 `CrossOrgPermissionDenied`），**动手前先验证目标仓库的事件权限能否拿到**。
- **验收**：在测试仓库开一个 PR 并留评论，确认事件进入漏斗、判定日志可见、结论按绑定关系回到指定群。

#### P1-2　投机执行从「只读查证」扩展到「沙盒复现」

- **现状**：`SilentInvestigationService` 的骨架完全正确（预算上限、证据分阈值、并发限制、冷却、审计表、丢弃即沉默），但它只会检索，不会复现。
- **要做什么**：允许静默调查在沙盒里执行复现步骤（本项目已有 `src/tools/sandbox` 与 `isolated-vm`），产出「最小复现步骤 + 现象」，仍然只读不落盘、不提交、不修改仓库。
- **为什么值**：把「我查过」升级为「我复现了」。而且 DeepSeek 的判据 —— 「确认问题存在**且**找到相对简单的修复方法才提交，否则全程安静」—— 与本项目已有的 `SILENT_INVESTIGATION_EVIDENCE_THRESHOLD` 语义完全对应，**可以直接复用现有阈值机制**，不需要新造一套门禁。
- **成本**：约 3 天。
- **风险与对策**：沙盒逃逸与资源占用 → 沿用现有 `maxWallTimeMs` / `maxTokens` / `maxConcurrency`，复现步骤必须在沙盒内且不触网（或走白名单）。
- **验收**：构造一个可复现的报错消息，确认调查产出复现步骤且证据分达标才浮出；不达标时审计表记录丢弃原因，群里完全静默。

#### P1-3　Creator mode 最小版：让 Agent 能起草技能，但不能自己启用

- **现状**：有 `skill-author` / `plugin-author` 说明书，但 Agent 侧只有 `skill_search` / `use_skill` / `skill_read` 三个只读工具，没有任何落盘路径。重复流程要沉淀成技能，必须管理员去控制台手写。
- **要做什么**：加一个 `risk=write` 的 `skill_draft` 工具，**只能写到 `SKILLS_LOCAL_DIR` 下的 `drafts/` 子目录，且写入后不自动启用** —— 必须管理员在控制台审核后才生效。
- **为什么值**：这是 A 文的核心洞察（「建设这个环境、接通这些能力，也可以让 Agent 自己参与」）。用最小代价拿到「对话里说一句就把它搭出来」，同时**不破坏**现有安全边界「技能正文只来自管理员维护的本地目录」。
- **成本**：约 2 天。
- **风险与对策**：
  - A 文的警告必须照抄进设计：来源、权限、可恢复版本都要看；涉及账号、外发、付费**不能因为「AI 帮我写的」就省掉确认**。→ 本项目已有的 `/confirm` 闸门与插件「保留最近两个版本可回滚」正好覆盖。
  - 草稿目录必须排除在技能加载路径之外，否则等于自动启用。
- **验收**：对话中让机器人把一个反复用到的流程写成技能草稿 → 确认文件落在 `drafts/` 且**未生效** → 管理员在控制台审核启用后才出现在技能目录。

### P2 — 低性价比，当前不建议做

#### P2-1　成熟 Agent Coach 新 Agent

A 文最有意思的部分，但对本项目**现在不该做**：它的前提是「有多个 Agent 实例」且「一个 Agent 能读取另一个 Agent 的会话」，而本项目已明确多机器人/多租户不在当前范围内。

**但它的产出物要拿走** —— 那三个失败模式已经拆到 P0-4，可以立即落地，不需要 Coach 机制本身。

#### P2-2　存算分离 / 本地 daemon

DeepSeek 的场景是「用户设备上有仓库，云端拿不到」。本项目部署目标是阿里云 ECS（systemd + Nginx + 同机自建 PG 16），仓库通过 `PROJECT_ALLOWED_ROOTS` 在服务端索引，「进程崩溃续跑」已由租约 + `SKIP LOCKED` 解决。做本地 daemon 等于新开一条产品线，成本极高、收益不明确。**不做。**

#### P2-3　Watchdog 换成 AI 监督员

本项目规则式看门狗已覆盖空转/重复/连续失败/预算四类异常，且可审计、行为可预测、**零额外 token**。换成 LLM 监督员会增加成本与不确定性，而 A 文自己也说「只加一句『你要认真一点』通常解决不了这些问题」。

**可选折中**（约半天）：只在规则式看门狗**已经判定异常之后**，让模型做一次「为什么卡住」的归因，写入审计供人复盘 —— **不接管干预决策**。干预权留在确定性规则手里。

#### P2-4　跨 Agent 需求交付链路（A 文第 3 点）

「用户在自己 Agent 里提问 → 需求进入专业同学 + 数据 Agent 的工作群 → 结果回流」依赖多机器人，同样不在当前范围内。P0-3 的事件直通做完后，这条的技术地基就有了，届时再评估。

---

## 五、执行建议

**顺序**：P0-4（半天，白拿）→ P0-1（1 天，解锁分派）→ P0-2（2 天，解决阻塞）→ P0-3（2–3 天，省 token + 上下文连续）→ 再评估 P1。

P0 四项加起来约 6 天，全部复用已有底座（WorkerRegistry、ScopedToolProvider、agent_jobs 队列与租约、RunWatchdog、agent_tasks/links、SilentInvestigationService），**不需要新建任何数据模型之外的基础设施**，也不触碰已稳定的钉钉入站与卡片流式链路。

**不要做的事**：不要因为 B 文的性能数字就去追「多 Worker 并行」。DeepSeek 自己说明了代价 —— Super-agent 的 cache 读取 token 高于单 Session，且实验用合成消息、未评估真实编码质量。本项目应该按自己的实际瓶颈排序：**当前的瓶颈是「同步串行导致的阻塞」和「模型无法自主分派」，不是并行度不够。**

## 六、一句话总结

本项目已经把 DeepSeek 列为「挑战」的东西（安全、长期记忆、进度可见、异常恢复）做完了，也已经独立实现了它的两个亮点（多级过滤、投机执行）；缺的是**调度层**——一个能让模型自己分派 Worker、不被长任务阻塞、并把后续事件接回同一件事的编排机制。这一层的所有零件本项目都已具备，只差组装。
